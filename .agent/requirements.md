## Данные и точный формат автоматической оценки

Постановка, страницы 11–14:

- Предусмотрены train_dataset.csv и private_features.csv. В reference train заявлено **99 955 строк**; фактические файлы в рабочую папку ещё не переданы и их схема не проверена.
- Ключ строки — anon_polygon_id + date. География анонимного ID не известна; самостоятельно придумывать соответствие реальному полю нельзя.
- primary_ndvi — согласованный целевой ряд. Постановка не задаёт точную формулу его объединения из сенсоров или их приоритет. Это нужно проверить по данным/разъяснениям; внешний ряд приложения описывать собственной явной схемой.
- Признаки включают спутниковые индексы, ERA5, календарь, климатологию, n_reference_years, crop_type, is_synthetic_gap. В train дополнительно есть ndvi_zscore и status, которых не будет в test.
- На контрольной строке is_synthetic_gap=True скрыты **primary_ndvi и остальные динамические и производные признаки этой строки**. Нельзя строить решение на предположении, что погода или индекс другого сенсора в этой строке останутся известны.
- Естественные пропуски сами по себе не входят в автоматическую метрику. submission содержит только все контрольные строки private_features с is_synthetic_gap=True.

```csv
anon_polygon_id,date,primary_ndvi_pred
```

Разделитель — запятая, кодировка — UTF-8, дата — YYYY-MM-DD, предсказание — конечное вещественное число. Множество пар ID+date должно точно совпадать с контрольными ключами; каждый ключ встречается один раз. Пропущенные, дополнительные, повторные строки и NaN недопустимы. Инженерный валидатор также отклоняет бесконечности.

```text
RMSE = sqrt(mean((primary_ndvi_true - primary_ndvi_pred)^2))
GapScore = round(30 * max(0, 1 - RMSE / 0.10), 2)
```

Метрика считается по всем контрольным точкам, а не как среднее RMSE отдельных полигонов. RMSE 0.08 даёт 6 баллов, 0.05 — 15, 0.02 — 24; RMSE ≥0.10 — 0. Локальные оценки и результат платформы показывать отдельно. Скрытые правильные значения private test доступны только организаторам. Отдельный submission со статусами аномалий не требуется (стр. 15).

## Рекомендации документов и решения команды

Статистические методы, классические алгоритмы, ML/DL и их сочетания разрешены; конкретная архитектура и нейросеть не предписаны (стр. 7). Выделенная ML-роль и Python — **решение команды по запросу пользователя**.

Среднее ближайших известных значений слева и справа — исходный пример baseline (стр. 8, 14). Интерполяция использует доступный контекст с обеих сторон: прежнее абсолютное запрещение будущих дат к этой ретроспективной задаче неприменимо. Если позже появится раннее онлайн-оповещение, для него нужен отдельный протокол без будущих наблюдений.

Z-score по климатологии и границы z≥−1, −2≤z<−1, z<−2 приведены как пример интерпретации (стр. 8–10). Можно выбрать другой обоснованный детектор. Проверка с исключением целых полей или сезонов рекомендована, но конкретный split документом не навязан.

Google Earth Engine, прямые API, Sentinel-2/Landsat/MODIS, ERA5/ERA5-Land, OSM/WorldCereal и дополнительные открытые данные перечислены как возможные источники. Рабочий маршрут выбирается после проверки доступа. Растровая маска сельхозпокрытия не становится готовыми границами отдельных полей без отдельной обработки.

Два реальных региона, ограничение размера запроса, выбор CPU-модели, Go-монолит с отдельным Python HTTP-сервисом в двух контейнерах и расписание на 48 часов — наши инженерные решения, а не требования к числу регионов или стеку от организаторов.
