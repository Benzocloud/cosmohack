## Продукт и две точки запуска

**Веб-приложение:** пользователь выбирает регион на карте, получает доступные сельхозконтуры или рисует свой полигон, добавляет его в список и запускает анализ за период. Сервис сам получает спутниковые и погодные данные, очищает наблюдения, восстанавливает пропуски и выделяет негативные периоды. На карте и графике видны исходные точки, восстановленные значения, сезонный фон, качество и объяснение. Участок можно удалить. Для первого рабочего интерфейса выбор региона — область карты/bbox; текстовый поиск места можно добавить позже.

**Технический batch:** команда принимает private_features.csv и создаёт submission.csv только по контрольным is_synthetic_gap=True. Запуск не требует веб-интерфейса. Формат и метрика заданы в requirements.md; отдельного submission по аномалиям нет.

Результаты соревнования по анонимным полям не привязывать к выдуманной географии. Веб-сценарий получает реальные геометрии из открытых источников/пользовательского ввода; преобразование его наблюдений к признакам модели документируется отдельно.

Файлы документации существуют; структура приложения и отчётов выше планируется. Прежний backend/internal/analysis/ не создаём: математикой владеет ML-пакет. Корневые frontend/ и backend/ сохраняются; ML остаётся внутри backend/, чтобы не нарушать выбранное разделение репозитория.

Go-образ содержит сервер и frontend/dist в /app/public. ML-образ содержит Python, пакет, зафиксированные зависимости и малый версионированный артефакт; большой артефакт доставляется по checksum и монтируется только для чтения до готовности ML. Модель загружается один раз на процесс; обучение не выполняется при сборке/старте сервисов. Один manifest связывает оба digest, версию HTTP-схемы, модель, профиль признаков и параметры. ML не публикует порт на хост и доступен Go по http://ml:8000; frontend вызывает только Go.

B3 владеет PostgreSQL repository: миграциями, embedded SQL, domain mapping, неизменяемыми версиями результатов и транзакционными переходами area/job/result. B4 создаёт pool и repository в application composition root, а также реализует один воркер (goroutine) и очередь до 8 ожидающих задач внутри Go, без отдельного контейнера воркера и внешнего брокера. POST публичного API возвращает 202 + job_id после сохранения и постановки задачи; переполнение очереди — 429, без зависшей queued-задачи. Воркер собирает данные B1, синхронно вызывает HTTP ML и сохраняет проверенный результат через B3; интерфейс получает статус опросом Go. ML выполняет максимум один расчёт и не хранит очередь/задания. Значения лимитов — стартовые настройки команды, уточняемые по первой реальной пробе.

Статусы заданий сохраняются; после рестарта Go прежние queued/running становятся failed с причиной interrupted, повторный запуск — явный. Удаление участка переводит его активные задачи в cancelled, отменяет ожидание HTTP и блокирует сохранение ответа для удалённой generation. Тайм-аут/разрыв HTTP не гарантирует остановку вычисления Python: ML удерживает занятый слот до фактического завершения и отвечает 429 на новый расчёт. Автоповторы POST не выполнять. Лимиты HTTP, валидация результата, ошибки и совместимость описаны в контракте.

Основной продуктовый блок B4 — `internal/service/analysis/` и `internal/service/ml/`: ограниченная очередь, вызов источников B1, вызов ML, проверка ответа, передача результата на сохранение B3, фактические стадии прогресса, тайм-ауты и обработка ошибок. Граница с B3: B3 принимает запрос и хранит задачу/результат, B4 выполняет работу и сообщает переходы состояния через согласованные операции B3. Особенности провайдеров остаются у B1, математические алгоритмы и HTTP-обработчик ML — у ML-разработчика.

B4 начинает с согласованных примеров входа/выхода и заглушек, не ждёт готовых модулей команды. В 0–4 ч — каркас, контракты и минимальная сборка/доставка; в 4–12 ч — исполнитель, ML-клиент и первый полный проход; в 12–24 ч — подключение и проверка реальных реализаций; в 24–48 ч — устойчивость, воспроизводимость и защита. Первый проход на заглушках нужен до подключения реальных источников, первый реальный сквозной сценарий остаётся целью к 8–12 ч. Ожидание SSH, merge, ML-модели или frontend не блокирует локальную работу над исполнителем. B4 исправляет свой интеграционный блок; ошибки отдельных модулей устраняют их владельцы по воспроизводимому примеру.

## Контракт первого часа

B4 первым локальным результатом в пределах 0–30 минут готовит минимальный Go-каркас: один backend/go.mod/go.sum по фактическим зависимостям и общие типы в backend/internal/domain/. Имя модуля — github.com/Benzocloud/cosmohack/backend; версию Go B4 фиксирует в go.mod и CI по проверенному окружению. Каркас не зависит от готовых B1/B3/ML/frontend или SSH. Для передачи каркаса действует общий цикл проверки и апрува; до его публикации другие владельцы продолжают доступные локальные задачи. В domain/ нет провайдеров, хранилища, HTTP-обработчиков или алгоритмов: source, store, api, jobs и mlbridge не должны образовывать цикл импортов.

| Сущность | Минимальные данные |
|---|---|
| Area / Contour | id, геометрия WGS84 longitude/latitude, источник контура, название, параметры периода |
| Observation | время/интервал, исходный primary_ndvi или null, маска качества, valid_fraction при доступности, индексы, погода с единицами и происхождением |
| Reconstruction | дата, восстановленное значение, observed/imputed/missing, метод/версия, доступный контекст; исходное значение не перезаписывается |
| AnalysisResult | восстановленный ряд, фон, негативные периоды, статус, тяжесть, численные основания, погодные гипотезы, ограничения и версии |
| Job | id, area_id, queued/running/completed/failed/cancelled, стадия обработки, причина ошибки, result_version |

Публичные маршруты: GET /api/regions/contours?bbox=…; GET/POST /api/areas; GET/DELETE /api/areas/{id}; POST /api/areas/{id}/analyses → 202 и job_id; GET /api/jobs/{id}; GET /api/areas/{id}/series?version=…; GET /api/areas/{id}/events?version=…; GET /api/config с публичными лимитами. Проверка готовности — /readyz. Отдельный endpoint растровых слоёв нужен только при их фактической реализации; карта полигонов не зависит от него. Актуальные расхождения существующего frontend с реализованным backend и порядок их устранения зафиксированы в [плане интеграции](plans/frontend-backend-integration.md).

Внутренние маршруты ML фиксированы отдельно: POST /v1/analyze (синхронный JSON, 200 с результатом) и GET /readyz (готовность модели и версии). Канонические поля запросов/ответов, ошибки, лимиты и правила версий — в [HTTP-контракте](contracts/go-ml-http.md). Публичный AnalysisResult формирует Go из проверенного ответа ML и метаданных B1/repository; браузер не обращается к ML напрямую. ML-01 и B4-01 должны поднять HTTP-заглушку на этом контракте к 2-му часу.

Параметры максимальной площади, длительности запроса и числа вершин определить по первой реальной пробе и показать пользователю до запуска. Эти ограничения не должны превращать интерфейс в жёсткий список заранее известных участков. Пустой каталог, плохая геометрия, частичные данные и отказ провайдера имеют разные ответы.

## Независимый старт четырёх направлений

Проверка планов 04.09.2026: локальную работу можно начать всем четырём одновременно. При этом кода общего Go-каркаса, общих JSON-фикстур и подключённых источников пока нет; действующий вход Go–ML — документированный HTTP v1. Не утверждать, что вся система уже собирается или что для конечной приёмки нет зависимостей.

| Владелец | Начинает сразу | Первый локальный результат | Внешняя зависимость для полной приёмки |
|---|---|---|---|
| B1 | Пробы Overpass/погоды/спутника, валидная тестовая геометрия, разбор и нормализация ответов | Пример контура и нормализованного ответа с качеством/происхождением; локальная проверка пустоты и ошибки | Доступ к провайдерам; общий Go-каркас для сборки пакета; интеграция с B4/B3 |
| ML | Python-пакет, синтетические ряды и маски, HTTP-адаптер по v1, baseline и CSV-валидатор | Проверяемый HTTP-ответ и batch на помеченном синтетическом наборе | Официальные CSV для оценки; реальные наблюдения B1 и клиент B4 для сквозной проверки |
| B3 | Контракт публичного API, операции снимков, состояния заданий; заглушки source/исполнителя | Хранилище и обработчики проходят локальные проверки без источников, ML и frontend | Общий Go-каркас для сборки; B4 для настоящего исполнения, B1/ML для реального результата |
| B4 | Минимальный Go-каркас, HTTP-клиент с собственным тестовым HTTP-сервером, исполнитель с заглушками | Каркас, проверяемый клиент и проход задача → данные → анализ → передача результата | Реальные B1/B3/ML/frontend для E2E; доступы к GHCR/SSH для доставки |

Подмена на время локальной разработки находится у потребителя: B3 подставляет источник/исполнитель, B4 — источник/хранилище и тестовый HTTP-сервер ML, ML — синтетический вход. Производственный модуль соседа не копируется и не реализуется вторым владельцем. Стыки B1 → B4, B4 → B3 и публичный API B3 пока требуют конкретизации Go-сигнатур/ответов в первом часу; согласование — параллельная задача владельцев, а не условие начала проб источников, хранения или Python-математики.

B1-03 начинается после локальной проверки геометрии, не после всей B1-02 до 12 ч. B3-02 не ждёт работающего сервера; B3-03 не ждёт ML-клиента для проверки API. B4 проверяет свой клиент до готовности HTTP-сервиса ML. ML-04 разрабатывается по HTTP-контракту, не ждёт завершения ML-03 с экспериментами или готового Go-пути. Первые реальные сквозные проверки остаются общим рубежом 8–12 ч.

Уточнение внутренних подэтапов разрешено каждому владельцу в своём плане по [инструкциям](instructions.md). Общие типы/фикстуры и изменения контрактов имеют одного ответственного за внесение и согласуются с потребителями; новый локальный подэтап не передаёт себе чужое владение и не меняет общую приёмку.

## Автоматический сбор данных

B1 до второго часа проверяет доступ к источникам для одного сельхозполигона и фиксирует основной путь:

- Контуры: [OSM Overpass API](https://wiki.openstreetmap.org/wiki/Overpass_API), доступные сельхозобъекты в bbox. Покрытие и смысл landuse не гарантируют кадастровые границы отдельных полей; показать происхождение. Собственный нарисованный полигон — второй обязательный путь, а не замена автоматическому поиску.
- Спутники: первым кандидатом остаётся [CDSE Statistical API](https://documentation.dataspace.copernicus.eu/APIs/SentinelHub/Statistical.html) с расчётом статистики на стороне провайдера; доступ/OAuth команды ещё не проверен. Уже работающий доступ участника к GEE может заменить этот путь по одному согласованному решению.
- Погода: [Open-Meteo Historical Weather API](https://open-meteo.com/en/docs/historical-weather-api) как кандидат для реанализа ERA5. Явно выбрать модель и переменные температуры/осадков, задать UTC и единицы; ERA5-Land имеет иной набор переменных, не считать модели взаимозаменяемыми. Погода относится к ячейке реанализа, а не измерению на поле.

Проверить лицензии, квоты и доступ; записать коллекции, параметры маски/агрегации и временные диапазоны в README и отчёт. Базовое число источников — спутник + погода + контуры. Объединение всех Sentinel/Landsat/MODIS в собственном веб-сборщике не является отдельным обязательством на 48 часов; использование нескольких сенсоров в предоставленном train проверяет ML.

Сохранять метаданные качества и NoData. Не обнулять отсутствующий NDVI, не смешивать NDWI разных определений, не принимать климатологию неизвестного происхождения за проверенную норму. Применимость модели к веб-данным проверяется по её входному контракту; при нехватке признаков использовать явно обозначенный резервный метод из того же пакета и показывать ограничение.

Контрольный исторический набор остаётся для устойчивой защиты. Он не доказывает автоматический сбор на новой территории; для него нужна отдельная реальная проверка. Регионы выбираются после проверки покрытия и доступа, с приоритетом сельхозугодий; Родос больше не является основным демонстрационным кейсом.

## ML и оценка

1. Проверить фактическую схему CSV, типы, уникальность ключей, маску и доли пропусков. Не использовать train-only status/ndvi_zscore как признаки инференса. Полный состав маскируемых столбцов определяется по полученным файлам.
2. Зафиксировать локальную проверку на исключённых полигонах/сезонах с искусственными одиночными и последовательными пропусками. На скрытых строках маскировать также динамические/производные признаки; рассчитывать признаки после маскировки. Проверить происхождение климатологии; статистики, зависящие от скрытых целей, пересчитать на разрешённом контексте или исключить.
3. Воспроизвести baseline организаторов: среднее ближайшего известного значения до и после пропуска. Отдельно сравнить линейную интерполяцию по времени; для краевых/длинных/полностью пустых сегментов определить проверяемые fallback-правила без NaN.
4. Сравнить с одним CPU-регрессором на признаках соседних наблюдений, расстояниях до них, сезонности и доступном контексте. Кандидат — [HistGradientBoostingRegressor](https://scikit-learn.org/stable/modules/generated/sklearn.ensemble.HistGradientBoostingRegressor.html); выбор и параметры определяются результатами, а не названием ML. PCHIP или сглаживание — ограниченная альтернатива, если остаётся время.
5. Локальный RMSE считать по всем скрытым контрольным точкам; срезы по полям, длине пропуска, краям и сезонам показывать отдельно. Зафиксировать seed, разбиение, маски, версии данных/кода и время. Проверить 2–3 содержательных сравнения, а не большой перебор.
6. Выбрать реально лучший метод, подготовить artifact manifest и строгий submission. Не выдавать локальную метрику за скрытый результат платформы; историю отправок и параметры финального файла сохранить.

Ретроспективное восстановление имеет доступ к известным значениям с обеих сторон пропуска. Это не прогноз будущей вегетации. Известные соседние даты удержанного поля допустимы как контекст восстановления, но его скрытые цели не используются для обучения/подбора. Набор признаков должен быть доступен в private_features, а не только в train.

Для аномалий стартовать с сезонного z-score или обоснованного устойчивого аналога. Статусы normal/candidate/confirmed/insufficient_data показывают состояние вывода; severity и величина z-score — отдельные поля. Подтверждение не означает установленную причину. Не превращать восстановленные моделью точки в независимые наблюдения, подтверждающие её же аномалию.

В объяснении разделять наблюдаемый спад, погодные факты, возможную причину и неопределённость. Уборка урожая, смена культуры и облачность — альтернативные объяснения, а не автоматически доказанные события. При короткой истории/неизвестной культуре показывать ограничение вместо выдуманной нормы или диагноза.

## UX и работа frontend

P0 включает адаптивное веб-приложение для компьютера, планшета и телефона. Мобильный просмотр карты, графиков и объяснений, а также основные действия с участками и анализом обязательны; макет на 390 px и проверка на телефоне входят в подготовку и приёмку интерфейса по design-brief.md.

Функциональные требования, сценарии, состояния, состав данных backend и готовый промпт собраны в [design-brief.md](design-brief.md). Передать его в Claude Design вместе с requirements.md. Сначала выбрать один из двух вариантов главного экрана, затем доработать состояния выбранного варианта и записать .agent/ui-spec.md. На выбор — до 90 минут; технический API-пример подключается параллельно.

B3 и B4 согласуют с B1, ML и frontend поля для графика, сводки, событий и прогресса по разделу 6 брифа в рамках первых контрактных этапов. Макет не подтверждает наличие данных или реализацию API. Основной интерфейс реализуется по выбранному дизайну и согласованным примерам; прежний эскиз и новый функциональный бриф сами по себе не являются апрувом макета.

## Рубежи команды

| Время от старта | Проверяемый результат |
|---|---|
| 0–2 ч | Прочитаны CSV либо явно отмечено их отсутствие; согласованы маска и владельцы; B1 проверяет 3 источника; ML фиксирует baseline/split и поднимает HTTP-заглушку; B4 подключает её Go-клиентом по контракту v1; B3 отдаёт пример; frontend выбирает макет |
| 4–6 ч | Рабочий baseline batch и валидатор CSV; реальные спутники + погода одного полигона; первый поиск контуров; оба образа и Compose прошли CI/GHCR/SSH, если выданы доступы |
| 8–12 ч | Воркер Go вызывает Python POST /v1/analyze; новый выбранный/нарисованный полигон проходит автоматический сбор → восстановление → аномалии → UI без ручного CSV; итоговая ML-модель ещё не нужна |
| 18–24 ч | Сопоставимые эксперименты и промежуточный submission; второй регион, удаление полигонов, частичные источники и длинные пропуски проверены |
| 28–32 ч | Выбран финальный метод, завершены основные возможности, зафиксированы версия модели и сценарий защиты |
| 32–36 ч | Чистый запуск обеих точек входа, итоговый submission, доступные артефакты, README и отчёт; исправления проверок проходят общий цикл |
| 36–48 ч | Презентация, репетиция, резервная запись и только критические исправления |

Отсутствующий CSV, доступ к провайдеру, Git/SSH или задержка проверки — явный блокер соответствующего результата. Локальную независимую работу продолжать по instructions.md, не отмечать удалённые проверки выполненными. Сроки включают время на два Sol-ревью, исправления и человеческий апрув каждого законченного этапа; чекбоксы не требуют отдельного апрува.

## CI/CD и воспроизводимость

Согласованный путь сохраняется: PR проверяет Go (race/lint/govulncheck), Python (lint, тесты маски/метрики/CSV/инференса), HTTP-контракт между ними, frontend (typecheck/build) и обе Docker-сборки без публикации. Main после успешных проверок публикует два образа в GHCR и автоматически развёртывает совместимую пару по SSH одним Compose-выпуском. Пользователь подтвердил внешний SSH-доступ; реквизиты ещё не получены.

Go-команды запускаются из backend/, Python — из backend/ml/, frontend — из frontend/. Docker context — корень. Версии runtime и зависимости зафиксировать; Go/Node caches указывают на backend/go.sum и frontend/package-lock.json. Actions фиксируются на проверенных SHA при реализации; packages:write доступен только publish job, публикация использует GITHUB_TOKEN.

Deploy получает immutable digest обоих образов и манифест выпуска, проверяет SSH host fingerprint, сериализует обновления и пропускает устаревший main. Обновление допускает короткий перерыв: приостановить приём анализов/остановить Go, обновить ML, проверить его /readyz и ожидаемые версии, запустить Go, проверить его /readyz и API. Go /readyz проверяет собственную готовность; ML readiness проверяется отдельно и не зависит от внешних источников. При провале вернуть предыдущую пару образов с совместимым артефактом и повторно проверить обе службы; первая неудачная установка без предыдущей версии считается ошибкой. Данные Go находятся в постоянном volume, секреты — в Secrets/серверной конфигурации. Приватный GHCR требует настроенного чтения пакетов на сервере.

README должен описать веб-запуск, неинтерактивный batch, обучение или загрузку готовой модели, внешние данные/лицензии, доступы, ожидаемые входы/выходы и ограничения. B4 проверяет инструкции на чистом окружении, ML передаёт команды и артефакты, B1 — источники и параметры. Все команды в плане пока проектируются; точные исполняемые команды появятся вместе с кодом и будут реально проверены.

## Финальная приёмка

- Есть batch-результат ровно по контрольным ключам; отсутствуют NaN, дубликаты и лишние строки.
- Есть baseline, сравнения и честные локальные RMSE/GapScore; полученный результат платформы подписан отдельно.
- Веб-сервис сам находит контуры и обрабатывает новый полигон со спутниками и погодой, поддерживает рисование и удаление.
- Исходный и восстановленный ряд различимы; аномалии, основания и ограничения доступны пользователю.
- Проверены два региона как командный тест переноса и отдельные отказы источников; восстановление не выдаётся за измерение.
- Две точки запуска воспроизводимы без правки исходников, артефакты доступны, README и исследовательский отчёт заполнены фактическими результатами.
- Комментарии к нетривиальному коду написаны по-русски; демонстрация и ответы на вопросы отрепетированы.

Открытые вопросы до реализации: фактические CSV и схема primary_ndvi/климатологии; доступы и лимиты источников; подходящие сельхозрегионы; ОС/архитектура/адрес/пользователь SSH, каталог и порт машины; формат/срок загрузки результата на платформу. Это не основания выдумывать данные или откладывать независимую работу.
