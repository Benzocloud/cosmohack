# План хакатона: восстановление NDVI и мониторинг сельхозтерриторий

Обновлено 04.09.2026 по двум документам организаторов. Команда: **3 backend + 1 ML + 1 frontend**, 48 часов. Бывший Backend №2 становится ML-разработчиком; номера B1, B3 и B4 сохраняются для остальных владельцев.

Требования и все 100 баллов разобраны в [requirements.md](requirements.md). Единый процесс разработки — [instructions.md](instructions.md). Это план: приложение, Git-репозиторий, remote, CI/CD, обработка датасетов и обучение ещё не выполнены. PDF сохранены в .agent/sources/; CSV, API-доступы, параметры машины и nickname участников пока отсутствуют.

## Продукт и две точки запуска

**Веб-приложение:** пользователь выбирает регион на карте, получает доступные сельхозконтуры или рисует свой полигон, добавляет его в список и запускает анализ за период. Сервис сам получает спутниковые и погодные данные, очищает наблюдения, восстанавливает пропуски и выделяет негативные периоды. На карте и графике видны исходные точки, восстановленные значения, сезонный фон, качество и объяснение. Участок можно удалить. Для первого рабочего интерфейса выбор региона — область карты/bbox; текстовый поиск места можно добавить позже.

**Технический batch:** команда принимает private_features.csv и создаёт submission.csv только по контрольным is_synthetic_gap=True. Запуск не требует веб-интерфейса. Формат и метрика заданы в requirements.md; отдельного submission по аномалиям нет.

Результаты соревнования по анонимным полям не привязывать к выдуманной географии. Веб-сценарий получает реальные геометрии из открытых источников/пользовательского ввода; преобразование его наблюдений к признакам модели документируется отдельно.

## Архитектура и монорепозиторий

Сохраняем **Go-монолит**, frontend и один развёртываемый образ. Добавляем Python-пакет внутри backend/ml/. Отдельный сетевой ML-сервис на старте не нужен: Go запускает фиксированную Python-команду на задачу, передаёт JSON через stdin и получает JSON через stdout. Пакет использует одни функции восстановления и аномалий в batch и веб-режиме.

Файлы документации существуют; структура приложения и отчётов выше планируется. Прежний backend/internal/analysis/ не создаём: математикой владеет ML-пакет. Корневые frontend/ и backend/ сохраняются; ML остаётся внутри backend/, чтобы не нарушать выбранное разделение репозитория.

В образе: Go-сервер, frontend/dist в /app/public, Python и зафиксированные зависимости. Обучение не выполняется при сборке/старте приложения. Малый итоговый артефакт включается в образ; для большого — воспроизводимая загрузка конкретной версии с checksum до готовности сервиса. Один manifest связывает код, модель, признаки и параметры.

B3 владеет простым файловым хранилищем: атомарные замены, сериализованная запись, неизменяемые версии результатов. B4 реализует ограниченное число выполняемых задач внутри Go, без внешнего брокера. Статус задания сохраняется; после рестарта прерванная работа становится failed с причиной и может быть явно перезапущена. Удаление участка отменяет его работу и не допускает повторного появления результата после удаления.

Запуск Python — через exec.CommandContext с фиксированным executable/module, без shell. Геометрия и параметры передаются данными; ограничить время, размер ввода/вывода и число одновременных процессов. Переход к постоянно работающему Python-сервису обсуждается только при измеренном ограничении этого подхода.

## Контракт первого часа

| Сущность | Минимальные данные |
|---|---|
| Area / Contour | id, геометрия WGS84 longitude/latitude, источник контура, название, параметры периода |
| Observation | время/интервал, исходный primary_ndvi или null, маска качества, valid_fraction при доступности, индексы, погода с единицами и происхождением |
| Reconstruction | дата, восстановленное значение, observed/imputed/missing, метод/версия, доступный контекст; исходное значение не перезаписывается |
| AnalysisResult | восстановленный ряд, фон, негативные периоды, статус, тяжесть, численные основания, погодные гипотезы, ограничения и версии |
| Job | id, area_id, queued/running/completed/failed/cancelled, стадия обработки, причина ошибки, result_version |

Предварительные маршруты: GET /api/regions/contours?bbox=…; GET/POST /api/areas; DELETE /api/areas/{id}; POST /api/areas/{id}/analyses → 202 и job_id; GET /api/jobs/{id}; GET /api/areas/{id}/series; GET /api/areas/{id}/events. Проверка готовности — /readyz. Отдельный endpoint растровых слоёв нужен только при их фактической реализации; карта полигонов не зависит от него.

Параметры максимальной площади, длительности запроса и числа вершин определить по первой реальной пробе и показать пользователю до запуска. Эти ограничения не должны превращать интерфейс в жёсткий список заранее известных участков. Пустой каталог, плохая геометрия, частичные данные и отказ провайдера имеют разные ответы.

## Автоматический сбор данных

B1 до второго часа проверяет доступ к источникам для одного сельхозполигона и фиксирует основной путь:

- Контуры: [OSM Overpass API](https://wiki.openstreetmap.org/wiki/Overpass_API), доступные сельхозобъекты в bbox. Покрытие и смысл landuse не гарантируют кадастровые границы отдельных полей; показать происхождение. Собственный нарисованный полигон — второй обязательный путь, а не замена автоматическому поиску.
- Спутники: первым кандидатом остаётся [CDSE Statistical API](https://documentation.dataspace.copernicus.eu/APIs/SentinelHub/Statistical.html) с расчётом статистики на стороне провайдера; доступ/OAuth команды ещё не проверен. Уже работающий доступ участника к GEE может заменить этот путь по одному согласованному решению.
- Погода: [Open-Meteo Historical Weather API](https://open-meteo.com/en/docs/historical-weather-api) как кандидат для реанализа ERA5. Явно выбрать модель и переменные температуры/осадков, задать UTC и единицы; ERA5-Land имеет иной набор переменных, не считать модели взаимозаменяемыми. Погода относится к ячейке реанализа, а не измерению на поле.

Проверить лицензии, квоты и доступ; записать коллекции, параметры маски/агрегации и временные диапазоны в README и отчёт. Базовое число источников — спутник + погода + контуры. Объединение всех Sentinel/Landsat/MODIS в собственном веб-сборщике не является отдельным обязательством на 48 часов; использование нескольких сенсоров в предоставленном train проверяет ML.

Сохранять метаданные качества и NoData. Не обнулять отсутствующий NDVI, не смешивать NDWI разных определений, не принимать климатологию неизвестного происхождения за проверенную норму. Применимость модели к веб-данным проверяется по её входному контракту; при нехватке признаков использовать явно обозначенный резервный метод из того же пакета и показывать ограничение.

Контрольный исторический набор остаётся для устойчивой защиты. Он не доказывает автоматический сбор на новой территории; для него нужна отдельная реальная проверка. Регионы выбираются после проверки покрытия и доступа, с приоритетом сельхозугодий; Родос больше не является основным демонстрационным кейсом.

## ML и оценка

1. Проверить фактическую схему CSV, типы, уникальность ключей, маску и доли пропусков. Не использовать train-only status/ndvi_zscore как признаки инференса. Полный состав маскируемых столбцов определяется по полученным файлам.
2. Зафиксировать локальную проверку на исключённых полигонах/сезонах с искусственными одиночными и последовательными пропусками. На скрытых строках маскировать также динамические/производные признаки; рассчитывать признаки после маскировки. Проверить происхождение климатологии; статистики, зависящие от скрытых целей, пересчитать на разрешённом контексте или исключить.
3. Воспроизвести baseline организаторов: среднее ближайшего известного значения до и после пропуска. Отдельно сравнить линейную интерполяцию по времени; для краевых/длинных/полностью пустых сегментов определить проверяемые fallback-правила без NaN.
4. Сравнить с одним CPU-регрессором на признаках соседних наблюдений, расстояниях до них, сезонности и доступном контексте. Кандидат — [HistGradientBoostingRegressor](https://scikit-learn.org/stable/modules/generated/sklearn.ensemble.HistGradientBoostingRegressor.html); выбор и параметры определяются результатами, а не названием ML. PCHIP или сглаживание — ограниченная альтернатива, если остаётся время.
5. Локальный RMSE считать по всем скрытым контрольным точкам; срезы по полям, длине пропуска, краям и сезонам показывать отдельно. Зафиксировать seed, разбиение, маски, версии данных/кода и время. Проверить 2–3 содержательных сравнения, а не большой перебор.
6. Выбрать реально лучший метод, подготовить artifact manifest и строгий submission. Не выдавать локальную метрику за скрытый результат платформы; историю отправок и параметры финального файла сохранить.

Ретроспективное восстановление имеет доступ к известным значениям с обеих сторон пропуска. Это не прогноз будущей вегетации. Известные соседние даты удержанного поля допустимы как контекст восстановления, но его скрытые цели не используются для обучения/подбора. Набор признаков должен быть доступен в private_features, а не только в train.

Для аномалий стартовать с сезонного z-score или обоснованного устойчивого аналога. Статусы normal/candidate/confirmed/insufficient_data показывают состояние вывода; severity и величина z-score — отдельные поля. Подтверждение не означает установленную причину. Не превращать восстановленные моделью точки в независимые наблюдения, подтверждающие её же аномалию.

В объяснении разделять наблюдаемый спад, погодные факты, возможную причину и неопределённость. Уборка урожая, смена культуры и облачность — альтернативные объяснения, а не автоматически доказанные события. При короткой истории/неизвестной культуре показывать ограничение вместо выдуманной нормы или диагноза.

## UX и работа frontend

До реализации основного интерфейса выбрать один из двух макетов в Claude Design и записать .agent/ui-spec.md. На выбор — до 90 минут; технический API-пример подключается параллельно. Новый промпт для макетов:

> Веб-сервис анализа сельхозполей. Пользователь выбирает область карты, видит найденные контуры или рисует свой полигон, добавляет/удаляет участки и запускает автоматический анализ за период. Покажи прогресс получения спутниковых данных, погоды и анализа. На графике явно различай исходные наблюдения, восстановленные пропуски и сезонный фон; выделяй негативные периоды. Карточка объясняет величину изменения, качество и погодные основания гипотезы. Предусмотри четыре статуса вывода, пустой каталог, ошибку источника, частичные данные, недостаточную историю и повторный запуск. Условные данные подпиши как пример.

Синхронизировать выбранный участок/период между картой и графиком. Реконструкцию обозначать пунктиром и текстом, исходные точки сохранять; не скрывать длинные пропуски. Погодные признаки доступны рядом с объяснением. Никаких «вероятностей засухи» или процентов повреждённой площади без расчёта и валидации.

## Рубежи команды

| Время от старта | Проверяемый результат |
|---|---|
| 0–2 ч | Прочитаны CSV либо явно отмечено их отсутствие; согласованы маска, JSON и владельцы; B1 проверяет 3 источника; ML фиксирует baseline/split; B3 отдаёт пример; B4 запускает Go + Python-контракт; frontend выбирает макет |
| 4–6 ч | Рабочий baseline batch и валидатор CSV; реальные спутники + погода одного полигона; первый поиск контуров; минимальный образ прошёл CI/GHCR/SSH, если выданы доступы |
| 8–12 ч | Python analyze работает через Go; новый выбранный/нарисованный полигон проходит автоматический сбор → восстановление → аномалии → UI без ручного CSV; итоговая ML-модель ещё не нужна |
| 18–24 ч | Сопоставимые эксперименты и промежуточный submission; второй регион, удаление полигонов, частичные источники и длинные пропуски проверены |
| 28–32 ч | Выбран финальный метод, завершены основные возможности, зафиксированы версия модели и сценарий защиты |
| 32–36 ч | Чистый запуск обеих точек входа, итоговый submission, доступные артефакты, README и отчёт; исправления проверок проходят общий цикл |
| 36–48 ч | Презентация, репетиция, резервная запись и только критические исправления |

Отсутствующий CSV, доступ к провайдеру, Git/SSH или задержка проверки — явный блокер соответствующего результата. Локальную независимую работу продолжать по instructions.md, не отмечать удалённые проверки выполненными. Сроки включают время на два Sol-ревью, исправления и человеческий апрув каждого законченного этапа; чекбоксы не требуют отдельного апрува.

## CI/CD и воспроизводимость

Согласованный путь сохраняется: PR проверяет Go (race/lint/govulncheck), Python (lint, тесты маски/метрики/CSV/инференса), frontend (typecheck/build) и Docker-сборку без публикации. Main после успешных проверок публикует один образ в GHCR и автоматически развёртывает его по SSH. Пользователь подтвердил внешний SSH-доступ; реквизиты ещё не получены.

Go-команды запускаются из backend/, Python — из backend/ml/, frontend — из frontend/. Docker context — корень. Версии runtime и зависимости зафиксировать; Go/Node caches указывают на backend/go.sum и frontend/package-lock.json. Actions фиксируются на проверенных SHA при реализации; packages:write доступен только publish job, публикация использует GITHUB_TOKEN.

Deploy получает immutable digest, проверяет SSH host fingerprint, сериализует обновления, пропускает устаревший main, ждёт настоящий healthcheck и проверяет /readyz плюс API. При провале возвращает предыдущий образ и совместимый артефакт модели; первая неудачная установка без предыдущей версии считается ошибкой. Данные находятся в постоянном volume, секреты — в Secrets/серверной конфигурации. Приватный GHCR требует настроенного чтения пакетов на сервере. Внешние спутниковые API не являются зависимостью /readyz.

README должен описать веб-запуск, неинтерактивный batch, обучение или загрузку готовой модели, внешние данные/лицензии, доступы, ожидаемые входы/выходы и ограничения. B4 проверяет инструкции на чистом окружении, ML передаёт команды и артефакты, B1 — источники и параметры. Все команды в плане пока проектируются; точные исполняемые команды появятся вместе с кодом и будут реально проверены.

## Финальная приёмка

- Есть batch-результат ровно по контрольным ключам; отсутствуют NaN, дубликаты и лишние строки.
- Есть baseline, сравнения и честные локальные RMSE/GapScore; полученный результат платформы подписан отдельно.
- Веб-сервис сам находит контуры и обрабатывает новый полигон со спутниками и погодой, поддерживает рисование и удаление.
- Исходный и восстановленный ряд различимы; аномалии, основания и ограничения доступны пользователю.
- Проверены два региона как командный тест переноса и отдельные отказы источников; восстановление не выдаётся за измерение.
- Две точки запуска воспроизводимы без правки исходников, артефакты доступны, README и исследовательский отчёт заполнены фактическими результатами.
- Комментарии к нетривиальному коду написаны по-русски; демонстрация и ответы на вопросы отрепетированы.

Открытые вопросы до реализации: фактические CSV и схема primary_ndvi/климатологии; доступы и лимиты источников; подходящие сельхозрегионы; URL GitHub и nickname; ОС/архитектура/адрес/пользователь SSH, каталог и порт машины; формат/срок загрузки результата на платформу. Это не основания выдумывать данные или откладывать независимую работу.
