**Архитектура и границы**

Разрабатывать Go-монолит, отдельный Python HTTP-сервис в backend/ml/ и frontend в одном репозитории. Два образа: Go с собранным UI и Python с ML-зависимостями/артефактом. Внутренний контракт — [go-ml-http.md](contracts/go-ml-http.md): POST /v1/analyze и GET /readyz. Go вызывает ML по HTTP из одного фонового воркера (goroutine) внутри Go-процесса; очередь ограничена, состояния и результаты принадлежат Go. ML выполняет синхронный расчёт без собственной очереди и хранилища заданий. Обучение не выполнять при сборке или запуске сервиса; модель загружается один раз на процесс до готовности. Нейросеть регламентом не предписана, итоговый метод выбирается по корректному сравнению.

Браузер обращается только к Go; адрес ML задаётся серверной конфигурацией, в Compose — http://ml:8000. Порт ML не публикуется наружу. Тайм-аут HTTP и удаление участка прекращают ожидание Go и блокируют сохранение позднего результата, но сами по себе не гарантируют остановку вычисления Python. ML допускает один фактически выполняемый расчёт и удерживает слот до его завершения; автоматические повторы POST не включать. Внешний брокер и отдельный контейнер Go-воркера для MVP не нужны.

Развивать параллельно две воспроизводимые точки запуска: автоматический веб-сценарий нового сельхозполигона и batch private_features.csv → submission.csv. Веб-сценарий включает поиск доступных контуров/рисование, спутники и погоду, восстановление, аномалии и объяснение. Сохранённый replay — резерв, который не заменяет автоматический сбор. Простым файловым хранилищем владеет Go: атомарная запись, версии результатов, сохранённые состояния заданий. Общую базу и дополнительные абстракции вводить при фактической необходимости.

Распределение владения:

- Backend №1 — `semennejo`: backend/internal/source/ — контуры, спутниковые и погодные данные, нормализация и происхождение.
- ML — `xsqclown`: backend/ml/ — восстановление, признаки, валидация, аномалии, HTTP-адаптер, batch CLI, модель и материалы исследования. Математику в Go повторно не реализовывать; HTTP и batch используют общие функции.
- Backend №3 — `tsuckermandev`: backend/internal/api/ и backend/internal/store/ — управление полигонами, API, хранение состояний заданий/результатов и кеш.
- Backend №4 — `globalarray`: выполнение анализа, интеграция и CI/CD: backend/cmd/server/, backend/internal/jobs/, backend/internal/mlbridge/, общие типы и сборка, Go-зависимости, deploy/, .github/, Dockerfile и backend/ml/Dockerfile. Основной блок — исполнитель задач, последовательность вызовов B1 и ML, прогресс, тайм-ауты и ошибки; B3 принимает запросы и сохраняет сообщённые исполнителем состояния/результаты. B4 начинает на согласованных заглушках, затем подключает реальные модули. Python-зависимости и ML-образ согласуются с ML; B4 собирает README и итоговый пакет. **Независимый старт и локальная детализация**

Все четыре направления — B1, ML, B3 и B4 — начинают локальную работу параллельно. Таблица первого результата и оставшихся зависимостей находится в разделе «Независимый старт четырёх направлений» общего плана. Независимость старта не означает отсутствие зависимостей при сквозной приёмке. В каждом этапе различать вход для локальной работы и внешний результат, необходимый для интеграционной проверки; ожидание второго не блокирует первое.

Разработчик может самостоятельно расширять свой персональный план подэтапами, например B1-03.1, и выбирать внутреннее устройство своего модуля. Детализацию хранить в своём файле .agent/plans/; большой раздел допустимо вынести в одноимённый подкаталог со ссылкой из персонального плана. Для подэтапа указать цель, свои файлы, входной контракт, результат и проверку. Подэтап наследует приоритет, ограничения, срок и критерии родительского этапа; дополнительная детализация не разрешает расширять MVP, переносить обязательный результат или ослаблять приёмку.

- Самостоятельно уточнять внутренние функции, локальные структуры, алгоритм в своей зоне, свои проверки и обработку ошибок в пределах согласованного контракта. Не требуется отдельное согласование каждой внутренней задачи.
- Изменения чужих файлов, владельца модуля, общего типа, HTTP/JSON/CSV-схемы, единиц, статусов, смысла ошибок, лимитов на стыке, хранения или поставки — общие изменения. До реализации согласовать их с затронутыми владельцами и обновить канонический контракт/план вместе с примерами. При отсутствии согласования продолжать независимые подзадачи; локальный план не переопределяет глобальные границы.
- Общими Go-типами, go.mod/go.sum, backend/testdata/ml-http/, обоими Dockerfile, Compose и корневым README владеет B4. B1/B3/ML передают предложения и примеры; B4 вносит согласованный общий diff. Семантику Go–ML согласуют B4 и ML, затронутые входы/выходы — также B1/B3. Python-зависимости и содержимое reports/research.md, reports/experiments.csv принадлежат ML. Код Python внутри backend/ml/ принадлежит ML, исключение — Dockerfile B4.
- Пока общего кода или примера нет, использовать локальные структуры и небольшие тестовые заглушки в своей зоне: B1 — source/testdata/, B3 — api/testdata/ и store/testdata/, B4 — jobs/testdata/ и mlbridge/testdata/ внутри backend/internal/, ML — backend/ml/tests/. Они следуют опубликованной схеме и не вводят альтернативный контракт. Общие примеры после согласования вносит B4; задержка их публикации не блокирует локальные примеры по документу.
- До публикации общего Go-каркаса B1 может проверять HTTP-ответы провайдеров, B3 — проектировать и проверять отдельные операции хранения в автономном временном тестовом каталоге вне репозитория. Не добавлять второй go.mod в source/ или store/, не создавать свою копию общих Go-типов как публичный контракт. После появления каркаса подключить свои пакеты и повторить их проверки в едином модуле. Полная Go-сборка до этого остаётся зависимостью от B4, а не заявленным результатом.
- Каждый разработчик работает в отдельной локальной копии/checkout. Не переключать ветку и не менять индекс в каталоге, где другой участник работает. Перед передачей перечитать свой diff: нет чужих файлов, нового внешнего контракта или незаявленной зависимости. Изменение общего файла выполняет его владелец одним согласованным diff; несколько агентов не переписывают его параллельно.

Локальная проверка на заглушке подтверждает поведение модуля. Реальные источники, фактические CSV, настоящий вызов Go → Python и удалённый deploy проверяются отдельно по исходным критериям; заглушка не закрывает эти требования и не становится основанием статуса done для всего этапа.

**Обязательный цикл каждого этапа**

Этап — законченный результат с ID из персонального плана, например ML-03. Подэтапы выполняются внутри него без отдельного апрува каждого чекбокса. Следующий зависимый этап начинается после выполнения его входных условий. При ожидании внешних доступов, merge или удалённой проверки можно продолжать независимую локальную работу следующих этапов, явно записав зависимость. Это не закрывает предыдущий этап и не отменяет его ревью, апрув или обязательные проверки; результаты и разрешения каждого этапа учитываются отдельно. Другие владельцы продолжают независимые задачи параллельно.

| Статус | Действие и условие перехода |
|---|---|
| planned | Прочитать входные условия, определить границы diff, ветку и базовый commit SHA |
| in_progress | Реализовать подэтапы и выполнить относящиеся к ним проверки |
| review | Передать один и тот же завершённый набор изменений двум независимым ревьюерам |
| fixes | Собрать оба отчёта и исправить все подтверждённые замечания |
| self_review | Лично перечитать итоговый diff и проверить исправления и критерии этапа |
| awaiting_approval | Показать ответственному разработчику итог и дождаться явного апрува этого этапа |
| published | После апрува создать согласованный commit, успешно отправить его в рабочую ветку и проверить результат push; дождаться проверок, которым нужна публикация |
| done | Подтвердить критерии этапа, включая требуемые результаты CI или развёртывания, и зафиксировать итог |

Если этап заблокирован, записать причину и доступную независимую работу; не выдавать блокировку за done. Незавершённую реализацию не отправлять на апрув как готовую. Ревью и все проверки, доступные без публикации, выполняются до запроса апрува. Если проверка требует нового workflow в GitHub или образа в GHCR, до апрува предъявить локальные проверки и точный план удалённой проверки; её результат получить после разрешённого push. До этого не заявлять, что CI или деплой уже прошли.

Для инфраструктурного этапа отдельно указать готовность изменений к апруву и доказательство завершения после публикации. Если необходим merge в main, его выполняет или отдельно разрешает ответственный разработчик; апрув на commit/push этого разрешения не заменяет. При ожидании такого merge или удалённой проверки этап остаётся published с указанной зависимостью. После ошибки новой проверки исправления проходят тот же цикл и новый апрув перед следующим commit/push.

**Модели и два независимых ревью в Codex**

Основная модель для реализации, исправлений и личного code review — Luna, идентификатор gpt-5.6-luna. Для фазы независимого ревью назначать Sol, идентификатор gpt-5.6-sol, явно при запуске ревьюеров.

1. После завершения реализации запустить read-only субагента на Sol со skill caveman-review. Он проверяет корректность, регрессии, обработку ошибок, контракты и достаточность относящихся к изменению проверок; замечания краткие, с местом, причиной и исправлением.
2. Параллельно запустить второго read-only субагента на Sol со skill ponytail-review. Он ищет лишнюю сложность, ненужные зависимости, дублирование и спекулятивные абстракции. Его задача не заменяет проверку корректности.
3. Дождаться обоих отчётов. Передать их исполнителю на Luna. Только исполнитель меняет код, затем сам проводит итоговый code review.

Обоим ревьюерам передать ID и цель этапа, критерии готовности, базовый SHA, список изменённых файлов, полный diff и результаты проверок. Включать новые неотслеживаемые файлы; одного git diff, который их не показывает, недостаточно. Во время двух ревью не менять этот набор файлов. Ревьюеры читают соответствующие SKILL.md и не редактируют файлы, не коммитят, не пушат и не выдают человеческий апрув.

Фраза «Luna → Sol → Luna» обозначает переход между исполнителем и фазой ревью. Если среда действительно позволяет сменить модель текущей задачи, смену необходимо подтвердить через её штатный механизм. В этой сессии доступен явный выбор модели субагента, а инструмент смены модели текущего ответа не предоставлен: рабочий вариант — оставить основную задачу на Luna и запустить двух Sol-субагентов. При выборе модели через collaboration.spawn_agent не использовать полный fork_turns=all вместе с model override; передавать ограниченный контекст или явное описание задачи. Не заявлять о переключении, если его не было, и не менять глобальную конфигурацию ради имитации переключения.

Выбор модели субагента предусмотрен [официальной документацией Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents). Фактическую доступность указанных моделей проверять по инструментам конкретной сессии. Если Sol, субагенты или нужный skill недоступны, подготовить материалы ревью и сообщить конкретный блокер; не считать обязательное ревью состоявшимся и не заменять модель или skill молча.

В Claude, Cursor или другом инструменте сохраняется тот же цикл двух ревью, исправлений, личной проверки и человеческого апрува. Требование идентификаторов Luna/Sol относится к Codex; вне Codex модель определяется возможностями и настройками команды, без утверждений о несуществующем переключении.

**Исправления, личный review и апрув**

Свести замечания двух ревьюеров в один список. Все подтверждённые недочёты исправить, включая замечания по избыточной сложности. Для ошибочного или неприменимого замечания привести проверяемое обоснование; спорные пункты явно вынести ответственному разработчику и не скрывать как исправленные.

После исправлений лично перечитать весь diff этапа, включая новые файлы. Проверить входные границы, ошибки, контракты, секреты, соответствие задаче и отсутствие случайных изменений. Выполнить проверки затронутого поведения. Если исправления меняют алгоритм, API, хранение, деплой или существенно перестраивают код, повторить релевантное Sol-ревью; новые подтверждённые замечания снова исправить до апрува.

Отчёт для апрува содержит ID этапа, итоговое поведение, изменённые файлы, результаты двух ревью, исправления, личную проверку, фактически выполненные команды и их результат, оставшиеся ограничения, целевую ветку и предлагаемый текст коммита.

Явный ответ ответственного разработчика «апрув», «approve» или равнозначное подтверждение относится к предъявленному результату конкретного этапа и разрешает commit и push в указанную ветку. Молчание и заключение субагента не являются апрувом. Не запрашивать повторное разрешение на уже одобренные commit и push. Если после апрува изменилось содержимое реализации или проверки выявили проблему, исправить её и заново предъявить изменённый результат.

**Ветки, коммиты и push**

До начала Git-работы определить настоящий nickname ответственного разработчика, целевой remote и базовую ветку. Не выдумывать nickname и адрес репозитория. Рабочую ветку можно создать в начале этапа; коммит и push выполняются только после апрува. Не включать чужие незавершённые изменения.

Имя ветки: <nickname>-backender/<type>/<short_description>. Type — feat, fix или chore; chore используется для инфраструктуры и служебных изменений. Short_description — короткое описание латиницей в lowercase с подчёркиваниями. Примеры с назначенными nicknames:

- xsqclown-backender/feat/seasonal_baseline
- semennejo-backender/fix/cloud_mask
- globalarray-backender/chore/ghcr_deploy

Перед использованием проверить имя через git check-ref-format --branch. Последовательные этапы одной задачи можно продолжать в согласованной рабочей ветке, сохраняя отдельный апрув и коммит каждого этапа. Для независимой задачи создавать отдельную ветку от согласованной актуальной базы. Если требуется зависимая ветка от ещё не интегрированной работы, явно согласовать её базу. Апрув этапа сам по себе не разрешает merge в main.

Текст коммита: feat: краткое описание, fix: краткое описание или chore: краткое описание. Выбрать тип по назначению изменения: функциональность, исправление ошибки или инфраструктура/обслуживание. Описание отражает результат, без фигурных скобок и шаблонных заглушек.

После апрува проверить итоговый diff и состав индекса, создать коммит и выполнить обычный push в согласованную рабочую ветку с upstream. Проверить, что remote указывает на ожидаемый commit, и сообщить SHA и имя ветки. При ошибке push этап не считается опубликованным. Не использовать force push и не переписывать чужую историю без отдельного указания. Не выполнять merge в main или ручной деплой как часть апрува этапа.

После успешного push статус published и SHA фиксируются в отчёте задачи. Когда выполнены все критерии, этап получает done; если дополнительных проверок после публикации нет, это происходит сразу после проверки push. Персональный план обновляется статусом в рабочей копии; запись может войти в следующий одобренный коммит, отдельный автоматический коммит только ради собственного SHA не создаётся. После merge проверенной ветки в main действует уже согласованный автоматический CI/CD.

**Данные и аналитика**

Хранить происхождение данных, интервалы и параметры обработки. Различать точную дату наблюдения и интервал агрегации. GeoJSON использует WGS84 и порядок longitude/latitude. Пропуск индекса — null; доля пригодной площади относится к полигону и находится в диапазоне 0–1.

Для ретроспективной интерполяции допустимы известные наблюдения до и после пропуска. Раннее онлайн-оповещение — отдельная задача без будущего контекста; его качество не заявлять по ретроспективной проверке. primary_ndvi из официального CSV не заменять самостоятельно выбранным индексом; соответствие веб-данных входу модели описать и проверить отдельно.

При локальной проверке контрольной строки скрывать primary_ndvi и динамические/производные признаки по схеме test. Строить признаки после маскировки. Train-only ndvi_zscore и status запрещены как признаки инференса. Проверить климатологию и другие производные на зависимость от скрытого target; при необходимости пересчитать из разрешённого контекста или исключить. Не включать целевой год в фон, которым измеряется его аномалия. Не выдумывать географию anon_polygon_id и не пытаться получить скрытые ответы через обход маски.

Batch сохраняет только все строки is_synthetic_gap=True: anon_polygon_id,date,primary_ndvi_pred, UTF-8, запятая, YYYY-MM-DD, каждый контрольный ключ ровно один раз, конечное число без NaN/Inf. Валидатор сравнивает множества ключей. RMSE считается по всем контрольным точкам; GapScore = round(30 * max(0, 1 - RMSE / 0.10), 2). Локальные метрики и платформенную оценку подписывать отдельно; отсутствующий результат не заменять ожидаемым.

Различать original/observed, imputed и missing: модельное восстановление не становится спутниковым измерением. Не подтверждать аномалию только её же восстановленными значениями. Низкое качество и недостаток истории дают понятное ограничение вывода. Score не является вероятностью; статус вывода и тяжесть изменения — отдельные поля. Синтетические проверки не доказывают качество на реальных событиях. NDVI и корреляция с погодой сами по себе не устанавливают причину; объяснение разделяет факты, гипотезу и ограничения.

Фиксировать seed, маску/split, версии данных/кода, конфигурацию и артефакты для каждого сравнения. В исследовательском отчёте сохранять baseline, гипотезы, сопоставимые эксперименты и выводы. Источники, внешние модели, лицензии, обучение и обе точки запуска описать в README. Содержательные комментарии к коду писать на русском по критериям организаторов; комментарии к очевидным операциям не добавлять ради количества.

**Frontend и совместная работа**

Поддержка компьютера, планшета и телефона входит в P0. Планировать мобильную компоновку и управление касанием вместе с основным интерфейсом; проверять просмотр результатов и основные действия в мобильном браузере. Не откладывать мобильную адаптацию без нового решения пользователя.

Вход для Claude Design — [design-brief.md](design-brief.md) и [requirements.md](requirements.md). Бриф определяет сценарии, визуализацию данных, состояния и требования к информации от backend. Сначала выбрать один из двух макетов главного экрана, затем доработать состояния выбранного варианта и зафиксировать взаимодействия в .agent/ui-spec.md до реализации основного интерфейса. Бриф не является утверждённым макетом или реализованным API. Начальный технический запуск и подключение согласованного API-примера можно делать параллельно. Прежний эскиз с фиксированными участками не является утверждённым дизайном нового сценария.

Caveman использовать для кратких рабочих ответов, ponytail — для ограничения сложности, Context7 — для актуальных API, Go-skills — по относящейся к задаче теме. Не подменять разработку настройкой инструментов. Инструкции и план писать понятным полным текстом.

**CI/CD и проверка**

Pull request запускает проверки и сборку двух образов. После успешных проверок main образы Go+frontend и ML публикуются в GHCR и автоматически развёртываются по SSH одним выпуском на машине команды. Ручное подтверждение каждого деплоя в этой схеме не требуется.

В CI Go-команды выполняются из backend/, Python-команды — из backend/ml/, frontend-команды — из frontend/. Кеши и настройки версий ссылаются на файлы соответствующего каталога. Обе Docker-сборки используют корень репозитория как context. Go-образ содержит сервер и frontend/dist/, скопированный в /app/public; ML-образ — Python runtime, пакет и версионированный артефакт. Один манифест выпуска связывает два digest, HTTP-схему, профиль признаков и модель; во время обновления приём новых анализов приостановлен до проверки совместимости.

Для развёртывания использовать точные digest обоих образов, проверку готовности обоих сервисов, последовательное обновление и явно реализованный возврат предыдущей совместимой пары с моделью. Go /readyz проверяет собственную готовность; deploy отдельно проверяет ML /readyz и совместимость выпуска. Данные хранятся вне контейнеров и переживают обновление; постоянными результатами владеет только Go. Секреты находятся в GitHub Secrets или конфигурации сервера; их не коммитить, не встраивать в frontend и не включать в образы.

Go-проверки включают тесты с race detector, lint и проверку уязвимостей; Python — lint, проверки маски/метрики/CSV и воспроизводимого инференса; граница Go–ML — HTTP-контракт, ошибки, лимиты и отмена; frontend — проверку типов и сборку. Дополнительные проверки выбирать по изменённому поведению. Для документации достаточно проверки путей, ссылок и согласованности; тестовые приложения для неё не создавать.

Каждый разработчик проверяет свой модуль. Backend №4 проверяет сквозной веб-сценарий, batch-запуск по README и развёртывание; ML подтверждает математическую корректность и артефакты. В отчёте отделять выполненную проверку от предположений и планов.
