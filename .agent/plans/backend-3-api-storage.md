# B3 — HTTP API и постоянное хранение (ответственный: `tsuckermandev`)

План рассчитан на 48 часов. Общий порядок `planned → in_progress → review → fixes → self_review → awaiting_approval → published → done`, два независимых ревью Sol, требования к веткам, апруву и публикации описаны в [общих инструкциях](../instructions.md). Этот файл детализирует только `backend/internal/api/` и `backend/internal/store/`; общие типы и запуск принадлежат B4.

## Журнал выполнения

**Старт без ожидания других владельцев:** описать публичные запросы/ответы по общему плану, разработать операции снимков и обработчики с локальными заглушками источника/исполнителя. Примеры и проверки находятся в backend/internal/api/testdata/ и backend/internal/store/testdata/; обработчики проверять тестовым HTTP-вызовом без настоящего сервера, ML или frontend. Полная Go-сборка использует каркас B4; до его передачи доступны детализация и автономные локальные проверки по общим инструкциям. Не создавать второй исполнитель или свой публичный вариант общих типов.

Для каждого ID вести запись: статус, базовый SHA, ветка,
проверки и результаты, два отчёта Sol и исправления, личное ревью, апрув, SHA
коммита и push, а также постпубликационные проверки. Пока все этапы planned:
ветки, SHA, проверки, ревью и апрув не заявлены.

## B3-01 — контракт и минимальные CRUD (0–2 ч)

**Статус:** planned

**Локальный вход:** общий план, HTTP v1 и небольшие примеры Area/Job/AnalysisResult, подготовленные в своей зоне. С B4 (`globalarray`) и frontend (`Prosteyshiyyy`) параллельно уточняются общий Go-тип и публичный JSON; работающие B1 (`semennejo`), B4, ML и frontend не требуются.

- [ ] Зафиксировать WGS84 GeoJSON с порядком longitude/latitude, UTC, `null` для отсутствующего индекса и безопасную семантику ошибок.
- [ ] Согласовать типы Area, Observation, SeriesPoint, Event, Job и AnalysisResult с B4; четыре UX-статуса (`normal`, `candidate`, `confirmed`, `insufficient_data`) хранить отдельно от severity и состояния job.
- [ ] Использовать [HTTP-контракт Go–ML](../contracts/go-ml-http.md) для полей результата и ошибок; публичный API дополняет проверенный ML-ответ метаданными B1/store, frontend обращается только к Go.
- [ ] Реализовать `GET/POST /api/areas`, `DELETE /api/areas/{id}`, `GET /api/areas/{id}/series` и `GET /api/areas/{id}/events`; не добавлять незапрошенные публичные маршруты.
- [ ] Реализовать согласованный с B1 поиск контуров `GET /api/regions/contours?bbox=...`; выбор региона идёт через bbox карты, текстовый поиск остаётся расширением.
- [ ] Принять полигон, параметры периода и источник; не делать фиксированный набор из 3–5 предвычисленных участков.
- [ ] Возвращать однозначные 400/404/409/429/500, включая 429 при заполненной очереди анализов, и не выдавать score как вероятность или NDVI как причину повреждения.

**Готово локально, если:** тестовый HTTP-клиент создаёт, читает, удаляет участок и получает пустой/демонстрационный ряд через обработчики B3. Публичный контракт B3 согласован с frontend/B4; переданные общие примеры вносит B4. Подключение настоящего frontend проверяется на рубеже интеграции, не является условием начала B3-01.

## B3-02 — постоянное файловое хранилище (2–6 ч)

**Статус:** planned

**Локальный вход:** структуры и контракт снимка из локальной части B3-01. Работающий сервер B4 не нужен: операции хранения проверяются в тестовом временном каталоге; сборка в общем Go-модуле — после передачи каркаса B4.

- [ ] Выбрать простые файлы снимков для участков, задач и результатов; сериализация принадлежит Go.
- [ ] Записывать через временный файл и атомарную замену, читать только завершённые снимки и переживать перезапуск.
- [ ] Хранить неизменяемые ключ и версию набора, геометрию, время, параметры, schema_version, feature_profile и model_version; связывать ответ ML с request_id/input_revision. Ключи анализов учитывают входной снимок и версии, смена модели не возвращает старый кеш.
- [ ] Различать исходные, восстановленные и отсутствующие данные через флаги и стиль/метаданные; восстановленное значение никогда не помечать наблюдением датчика.
- [ ] Обеспечить безопасное удаление участка и сохранение состояния задачи без Redis, внешней БД или обязательного общего кеш-сервиса.

**Готово, если:** процесс после перезапуска читает полный снимок, конкурентная запись не отдаёт обрезанный JSON, а изменение любого ключевого параметра создаёт новый неизменяемый результат.

## B3-03 — задачи и граница исполнителя (6–12 ч)

**Статус:** planned

**Локальный вход:** операции хранения B3-02 и согласованные состояния задачи; источник и исполнитель заменяются тестовыми заглушками B3. HTTP-клиент ML и worker B4 нужны для сквозной приёмки, не для разработки job API.

- [ ] Реализовать `POST /api/areas/{id}/analyses` с ответом `202` и `job_id`, `GET /api/jobs/{id}`, `GET /api/areas/{id}/series` и `GET /api/areas/{id}/events` с готовым результатом.
- [ ] Передавать job B4 через один воркер-goroutine и очередь до 8 ожидающих внутри Go: B4 координирует B1 и HTTP ML, B3 сохраняет переходы и результат. Возвращать 202 только после сохранения/постановки; при переполнении — 429 без бесхозной queued-задачи.
- [ ] Отменённую задачу помечать `cancelled`; прерывание, тайм-аут или ошибка помечаются `failed` с кодом из HTTP-контракта. После рестарта queued/running становятся failed/interrupted. Повторный запуск — явным новым действием с новым job ID, автоматических HTTP-повторов нет.
- [ ] HTTP 200 от ML с `insufficient_data` сохранять как completed со статусом вывода и ограничениями; `ml_busy`, `ml_timeout`, `ml_unavailable` и невалидный ответ — failed. GET job возвращает 200 со статусом задачи, не проксирует HTTP-ошибку ML.
- [ ] Удаление активного полигона отменяет ожидание HTTP и блокирует запись результата по старому area generation/терминальному состоянию job. Не обещать остановку вычисления Python из-за разрыва HTTP; поздний ответ не сохранять.
- [ ] Проверить состояния queued/running/completed/failed/cancelled и повторяемое чтение результата.
- [ ] К 12-му часу провести первый реальный путь нового полигона: bbox или draw → B1 satellite/weather → Python analysis → сохранённый результат → API.

**Готово, если:** первый новый реальный полигон проходит отправку → состояние → сохранённый результат к 12-му часу, активное удаление не возвращает результат, а тайм-аут или ошибка HTTP ML видны как `failed` с причиной; недостаток данных сохраняется отдельно от технического сбоя.

## B3-04 — реальный ряд и качество (12–24 ч)

**Статус:** planned

**Локальный вход:** сохранённый AnalysisResult по схеме с наблюдениями/восстановлением/пропусками; примеры можно подготовить самому в своей тестовой зоне. Реальные наблюдения B1 и выполнение через ML/B4 нужны для приёмки на двух регионах; B3 не загружает модель и не обращается к ML напрямую.

- [ ] Подключить один реальный сохранённый ряд через согласованный `AnalysisResult`; расчёт не дублировать в API.
- [ ] Передавать периоды, сезонный фон, аномалии, объяснение, происхождение, идентификаторы сцен при их наличии, источник погоды и флаги качества.
- [ ] Независимо отражать четыре статуса интерфейса и тяжесть; не выдавать историческую проверку за оперативное оповещение.
- [ ] Передавать результат и флаги краевого резервного метода, который предоставляет ML-пакет; B3 не реализует собственный алгоритм интерполяции и явно отмечает реконструкцию.
- [ ] Расширить первый реальный путь вторым регионом, проверкой качества, облачности, недоступности источника и устойчивости к 24-му часу; синтетическая фикстура первого развёртывания остаётся отдельно помеченной и не подменяет реальный результат.

**Готово, если:** два региона проходят источник → анализ → хранилище → API, включая проверку качества и отказ источника, а клиент различает исходные, восстановленные и отсутствующие данные и видит объяснение и происхождение.

## B3-05 — ошибки, API-передача и приёмка (24–36 ч)

**Вход:** B3-01…04 и интеграционный сценарий B4.

- [ ] Повторно проверить выбор области карты и `GET /api/regions/contours?bbox=...`, уже подключённые с B1/B4 в B3-01/B3-03; текстовый поиск оставить расширением.
- [ ] Проверить путь интерфейса: новый регион → доступные контуры или рисование → сбор спутниковых и погодных данных → очищенный исходный и восстановленный primary NDVI → сезонный фон и периоды аномалий → объяснение → карта и график; добавление и удаление работают динамически.
- [ ] Растровые слои `/layers` добавлять только при выбранной дополнительной потребности; основной пользовательский путь от них не зависит.
- [ ] Проверить неверный GeoJSON, недопустимый bbox/период, отсутствующий набор, устаревший ключ, удалённый участок, отказ источника, ошибку Python, тайм-аут и повреждённый снимок.

**Готово, если:** новая область и область пользователя проходят полный основной сценарий, ошибки не маскируются как completed/normal, а постоянное хранилище и API проверены локально и в сквозном тесте.

**Критерии B3:** CRUD и контракт поиска контуров на фикстуре к 2 ч, постоянные снимки к 6 ч, первый реальный новый полигон, задачи и поиск к 12 ч, второй регион и устойчивость качества к 24 ч, полный сценарий интерфейса и передача к 36 ч. Остаток до 48 ч — только исправления и повторные проверки по общему циклу; незавершённое не отправлять на апрув.
