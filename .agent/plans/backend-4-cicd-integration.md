# B4 — общие типы, Python bridge, сборка, CI/CD и интеграция

План рассчитан на 48 часов. Общий порядок этапов, два независимых ревью Sol,
апрув, commit/push и правила публикации определены в [общих инструкциях](../instructions.md).
B4 владеет `backend/cmd/server/`, общими типами, Python-мостом, Dockerfile, CI/CD,
`deploy/`, README и сквозной проверкой; B3 владеет API/store, B1 — source,
ML-владелец — пакет Python, артефакты и исследование, frontend-владелец — `frontend/`.

## Журнал выполнения

Для каждого ID фиксировать статус, базовый SHA, настоящий nickname и ветку,
проверки, оба отчёта Sol и исправления, личное ревью, апрув, SHA/push,
послепубликационные результаты и blockers. Все этапы изначально planned.

## B4-01 — Go-модуль, типы и Python-мост (0–2 ч)

**Статус:** planned

**Вход:** решения `.agent/plan.md`, контракты B1/B3/ML/frontend.

- [ ] Поднять один Go-модуль в `backend/`, `backend/cmd/server/` и `/readyz`; команды запускаются из `backend/`.
- [ ] Согласовать и закрепить общие типы для геометрии, наблюдений, ключа набора, состояний задачи, происхождения, флагов качества/данных, сезонных периодов и объяснения.
- [ ] Реализовать ограниченный мост к пакету `backend/ml/vegetation_ml` через `exec.CommandContext`: фиксированный модуль Python, JSON stdin/stdout, тайм-аут/отмену, ограничение размера и времени, проверку схемы.
- [ ] Не запускать HTTP-сервис ML, shell, Redis-брокер или обучение внутри Docker; одни функции Python должны использоваться для веба и batch.
- [ ] Зафиксировать версию артефакта/модели, совместимую с digest выпуска; артефакты входят в образ или монтируются только для чтения по версии.

**Готово, если:** Go server локально вызывает заглушку или предоставленный API Python, неверный JSON/тайм-аут даёт ошибку, а интерфейс получает согласованные проверку готовности и типы.

## B4-02 — единый образ и первая доставка (2–6 ч)

**Статус:** planned

**Вход:** B4-01, API fixture B3, frontend build.

- [ ] Подготовить корневой многоэтапный Dockerfile: собрать `frontend/`, собрать Go из `backend/`, установить среду Python и пакет/артефакты; итоговый образ содержит Go server и `/app/public`.
- [ ] Не обучать модель в Docker и не запускать отдельные сервисы; первое развёртывание допускает baseline fixture с явной пометкой.
- [ ] Подготовить Compose/deploy с постоянным томом для снимков, точным digest образа, readiness, последовательным обновлением, сохранением предыдущего digest и откатом.
- [ ] До deploy проверить фактические SSH fingerprint/key, каталог, порт, registry permissions; отсутствующие доступы записать blocker, scaffold не считать deploy.
- [ ] Реализовать проверки PR/main: тесты Go с race detector, lint, govulncheck, проверку типов и сборку frontend, lint Python, целевые тесты и строгий CSV-контракт, Docker build; публиковать GHCR только для main через `GITHUB_TOKEN`, выдав `packages:write` только задаче публикации.
- [ ] Перенести в `README.md` команды запуска Go, Python-моста, веба и batch, соответствие версий артефактов и отката уже на этом этапе (0–6 ч).

**Готово к approval, если:** локальные сборки и проверки, образ, Compose и скрипт доставки проверены. После approval выполняются commit/push рабочей ветки, отдельный разрешённый merge в main, зелёный CI, фактическая публикация GHCR и первый SSH deploy с readiness к 6-му часу; после успешного push этап становится published, после проверки digest и доступности стенда — done. При ожидании доступа или merge остаётся published с указанной зависимостью. Автодеплой после зелёного main выполняется разрешённым workflow без отдельного подтверждения каждого deploy.

## B4-03 — сквозная веб-интеграция и batch (6–12 ч)

**Статус:** planned

**Вход:** B4-02, B1 source, B3 API/store, ML artifacts/API, frontend.

- [ ] Соединить bbox карты и поиск контуров, пользовательский полигон, сбор спутниковых и погодных данных B1, отправку/состояние/результат B3 и карту/график интерфейса; текстовый поиск и растровые слои оставить необязательными.
- [ ] Координировать задачи внутри процесса с ограниченным числом исполнителей; B3 сохраняет состояние. Отменённые задачи — `cancelled`, прерванные и ошибочные — `failed` с причиной; повторный запуск явный; удаление активного участка отменяет работу и не допускает воскресшего результата.
- [ ] Проверить основной путь: очищенный исходный и восстановленный primary_ndvi, сезонный фон, периоды аномалий и объяснение, с независимыми флагами/стилем исходных, восстановленных и отсутствующих данных и четырьмя статусами интерфейса.
- [ ] Передать ML-владельцу и B3 общую схему моста; результаты веба и batch должны использовать одни функции Python.
- [ ] Принять от ML-владельца независимую неинтерактивную batch CLI: `private_features.csv` → `submission.csv`, конечные числовые значения, уникальные ключи и детерминированная схема; B4 интегрирует, проверяет и документирует её, но не реализует вторую CLI.
- [ ] Запустить до 12 ч первый end-to-end сценарий и зафиксировать, что реально проверено, а что зависит от внешних доступов.

**Готово, если:** новая область и рисование работают автоматически, пакетный запуск воспроизводим отдельно от веба, а реальный и демонстрационный пути имеют проверяемые результаты без ложного успеха.

## B4-04 — CI, staging и устойчивость (12–24 ч)

**Статус:** planned

**Вход:** B4-03 и доступы к repo/registry/staging.

- [ ] Проверить PR checks и main-only публикацию, версии из `backend/go.mod`, `backend/go.sum`, `frontend/package-lock.json`; Docker build всегда с корневым context `.`.
- [ ] Проверить на staging точный digest, `/readyz`, реальный запрос данных, сохранность тома, корректную отмену, откат и повторный запуск; подтвердить сохранённое доказательство первой доставки из B4-02.
- [ ] Убедиться, что frontend не содержит секретов, host уже доступен извне, deploy не перекрывает более новый main, а SSH fingerprint проверяется.
- [ ] Проверить устойчивость и второй реальный регион к 24 ч; historical review не выдавать за live alert.

**Готово, если:** staging реально обновлён и проверен, CI даёт требуемые проверки, данные переживают обновление, откат проверен и два региона имеют доказательства качества. Если внешний доступ отсутствует, этап остаётся незавершённым с явно записанным blocker; локальная работа не выдаётся за actual deploy.

## B4-05 — заморозка и защита воспроизводимости (24–48 ч)

**Статус:** planned

**Вход:** B4-04, результаты B1/B3/ML/frontend и доступный staging.

- [ ] До 32 ч заморозить scope: только критические fixes; primary UX не блокировать optional `/layers` или текстовым поиском.
- [ ] К 36 ч получить независимо воспроизводимые веб- и batch-точки запуска, отчёт `reports/research.md`, версии артефактов/весов и submission output; ML-владелец поставляет содержание исследования, B4 проверяет упаковку.
- [ ] Проверить презентацию 2–3 временных рядов, ограничения признаков/происхождения, provenance, стили исходных/восстановленных/отсутствующих данных, смысл score и маркировку синтетики.
- [ ] Провести финальный E2E с добавлением/удалением полигона, interruption/failure/retry, двумя реальными регионами и restart persistence.
- [ ] Завершить этап по общему циклу: два Sol-ревью, исправления, личная проверка и апрув. 36–48 ч оставить на репетицию и критические исправления; блокеры записать явно.
- [ ] Не заявлять успех без фактического зелёного CI, опубликованного digest и actual deploy; при отсутствии remote/SSH/registry указать точный внешний blocker и продолжить независимые локальные проверки.

**Критерии B4:** мост, общие типы и запускаемый сервер к 2 ч; локальная готовность образа и CI к 6 ч, затем фактические GHCR/SSH deploy и проверка digest; веб-интеграция и batch к 12 ч; staging, устойчивость и второй регион к 24 ч; freeze к 32 ч; воспроизводимые точки запуска, `reports/research.md`, артефакты и submission к 36 ч; готовность защиты — 36–48 ч. Approval этапа разрешает только его согласованный commit/push; merge в main выполняется разрешённым процессом, а deploy запускается автоматически после зелёного main.
