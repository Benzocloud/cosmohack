# Контракт Go ↔ ML по HTTP, v1

Решение команды для MVP, зафиксировано 04.09.2026. Это спецификация для реализации;
сервис, клиент и перечисленные проверки пока не реализованы. Общий план —
[plan.md](../plan.md). Владельцы: B4 — `globalarray` (клиент и интеграция),
ML — `xsqclown` (HTTP-адаптер и вычисления), B1 — `semennejo` (входные
данные), B3 — `tsuckermandev` (задачи, хранение и публичное API).

## Граница ответственности

Go собирает спутниковые и погодные данные, нормализует их, хранит полигоны/задачи/
результаты и вызывает ML из фонового воркера. Python получает готовые данные,
восстанавливает ряд и вычисляет аномалии. Собственных очереди, job API, базы,
скачивания источников и обратных вызовов в Go у ML нет. Геометрия остаётся в Go;
для расчёта передаются идентификатор участка и числовой контекст.

В Compose имя сервиса — `ml`, адрес в конфигурации Go `ML_BASE_URL=http://ml:8000`.
Порт ML не публикуется на хост, frontend обращается только к Go. Адрес ML задаётся
оператором, не принимается из пользовательского запроса. В локальном запуске
вне Compose допускается `http://127.0.0.1:8000`. Обучение — отдельная команда;
сервис загружает версионированную модель один раз на процесс до готовности.

## Маршруты и версии

| Метод и путь | Успешный ответ | Назначение |
|---|---|---|
| `POST /v1/analyze` | `200 application/json` | Синхронный расчёт одного участка и периода |
| `GET /readyz` | `200 application/json` | Модель загружена, конфигурация и схема готовы |

Запрос анализа: `Content-Type: application/json`, `Accept: application/json`.
Кодировка UTF-8, имена JSON-полей snake_case. Ответ ML не содержит `202` или
`job_id`: асинхронность и job API принадлежат Go. `request_id` равен ID задачи Go
и возвращается без изменения; это корреляция, не механизм дедупликации.

Начальная `schema_version` — строка `1.0`. Обе стороны проверяют точное совпадение
версии; неизвестные поля запроса отклоняются, поля ответа проверяются по этой
схеме. Расширения согласуют B4/ML/B1/B3 и обновляют здесь вместе с примерами и
проверками до изменения реализаций; несовместимое изменение требует `/v2`.
Версия модели не является версией HTTP-схемы.

## Запрос анализа

| Поле | Тип и смысл |
|---|---|
| `schema_version` | Строка `1.0` |
| `request_id` | Непустая строка, ID текущей задачи Go |
| `area_id` | Непустая строка, ID реального веб-участка |
| `input_revision` | Непустая строка, версия неизменяемого входного снимка Go |
| `mode` | Только `retrospective` в MVP |
| `feature_profile` | Только `ndvi-weather-v1` в начальном веб-контракте |
| `analysis_period` | Объект `from`, `to`: даты `YYYY-MM-DD`, обе границы включены |
| `sources` | Массив источников по схеме ниже, ID уникальны |
| `observations` | Массив точек по схеме ниже, даты уникальны и строго возрастают |

Все поля верхнего уровня обязательны. Строки ID/версий — до 128 символов.
Дата относится к UTC; начало analysis_period не позже конца. Контекст до/после анализируемого периода допустим для
ретроспективного восстановления; ML возвращает точки только внутри периода.
Go явно создаёт точки с `null` на датах, которые надо восстановить. ML не
вставляет новые даты и не выбирает временную сетку самостоятельно.

Источник: обязательные `id`, `kind` (`satellite`, `weather` или `reference`),
`provider`, `dataset`, `mapping`, `retrieved_at` (RFC3339 UTC); `license` — строка
или `null`, обязательна. `dataset` включает известную версию продукта; `mapping`
описывает агрегацию, единицы и сопоставление целевого индекса/погодной ячейки.
Неизвестные версии явно обозначаются в описании. Секреты и URL с токенами сюда
не входят. Подробную геометрию, сцены и лицензирование B1 сохраняет в снимке Go.

| Поле точки | Тип и смысл |
|---|---|
| `date` | Дата `YYYY-MM-DD`, ключ точки |
| `primary_ndvi` | Конечное число или `null`; исходное значение сохраняется |
| `quality` | `usable`, `unusable` или `missing`; при `null` — `missing` |
| `ndvi_source_id` | ID источника `satellite` или `null`, если наблюдение отсутствует |
| `interval` | `{from, to}` с включёнными датами агрегации; `null`, если нет наблюдения |
| `valid_fraction` | Число от 0 до 1 или `null`, доля пригодной площади полигона |
| `missing_reason` | Строка или `null`; причина отсутствия/отбраковки |
| `weather` | Объект ниже или `null` |
| `reference` | Объект ниже или `null` |

Все поля точки обязательны, отсутствие данных кодируется `null`, не нулём.
`usable` требует числовой NDVI, источника и интервала; `unusable` сохраняет
числовое исходное значение с причиной отбраковки и не используется как надёжное
наблюдение; источник и интервал при `unusable` тоже обязательны. При числовом
NDVI дата лежит внутри его интервала, начало интервала не позже конца. У точки
`missing` обязателен `missing_reason`. Нельзя размножать одно
многодневное наблюдение на несколько дней как независимые измерения.

`weather`: обязательные `source_id` (источник `weather`), `temperature_mean_c`
(средняя температура за день UTC, °C, число или `null`), `precipitation_sum_mm`
(осадки за день UTC, мм, неотрицательное число или `null`). Это данные реанализа,
не измерения на поле. Один и тот же день не агрегируется повторно внутри ML.

`reference`: обязательные `source_id` (источник `reference`), `mean` (число),
`std` (неотрицательное число), `n_reference_years` (положительное целое),
`target_year_excluded` (только `true`). B1/ML подтверждают происхождение и
исключение года точки до передачи; иначе передают `null`. При нулевой `std`
z-score не определяется. Одного поля `true` без проверки происхождения
недостаточно. Если ML строит фон сам, метод и разрешённая история фиксируются
в версии метода и ограничениях результата.

Профиль фиксирует только веб-вход. NDWI/EVI, crop_type и другие признаки не
добавляются произвольным словарём: расширение профиля согласуется после проверки
реальных данных. При нехватке признаков выбранной модели ML использует явно
обозначенный резервный метод либо возвращает недостаток данных. Схема официального
CSV, его маскирование и train-only признаки остаются отдельным batch-контрактом.

Пример условного запроса с недостатком наблюдений, не реальный датасет:

```json
{
  "schema_version": "1.0",
  "request_id": "job-example-1",
  "area_id": "area-example-1",
  "input_revision": "input-example-1",
  "mode": "retrospective",
  "feature_profile": "ndvi-weather-v1",
  "analysis_period": {"from": "2026-06-01", "to": "2026-06-01"},
  "sources": [],
  "observations": [
    {
      "date": "2026-06-01", "primary_ndvi": null, "quality": "missing",
      "ndvi_source_id": null, "interval": null, "valid_fraction": null,
      "missing_reason": "no_usable_observation", "weather": null, "reference": null
    }
  ]
}
```

## Результат анализа

Обязательные поля: `schema_version`, `request_id`, `area_id`, `input_revision`,
`mode`, `feature_profile` (эхо запроса), `model_version` (версия загруженного
артефакта/набора методов), `method` (реально выбранный метод), `status`,
`severity`, `series`, `events`, `limitations` (массив строк).

`status`: `normal`, `candidate`, `confirmed`, `insufficient_data`.
`severity`: `none`, `moderate`, `high` или `null`; при `insufficient_data` —
`null`, при `normal` — `none`, иначе `moderate`/`high`. Границы тяжести относятся
к версии детектора. `confirmed` означает подтверждённое отклонение, не доказанную
причину. Нет отдельного некалиброванного `confidence` или вероятности засухи.

Каждая точка `series` содержит обязательные поля:

| Поле | Значение |
|---|---|
| `date` | Дата исходной точки |
| `primary_ndvi` | Неизменённое исходное значение, включая `null` |
| `value` | Итоговое значение: наблюдение, восстановление или `null` |
| `state` | `observed`, `imputed` или `missing` |
| `method` | Метод восстановления для `imputed`, иначе `null` |
| `baseline` | Сезонный фон или `null`, если его нельзя обосновать |
| `z_score` | Конечное число или `null`; неизвестный фон/нулевая дисперсия → `null` |

В ответе ровно по одной точке на каждую входную дату внутри `analysis_period`,
в том же порядке. Каждый входной `usable` сохраняется как `observed`, `value`
равен исходному NDVI; остальные точки не могут стать `observed`. `imputed` имеет конечное `value` и метод; `missing` имеет
`value=null`. При достаточных наблюдениях для восстановления, но недостатке
фона детекции, допустим восстановленный ряд со статусом `insufficient_data`.

Событие `events[]`: обязательные `start_date`, `end_date` (внутри периода,
начало не позже конца), `status` (`candidate`/`confirmed`), `severity`
(`moderate`/`high`), `min_z_score` (число или `null`), `evidence_dates` (массив
дат надёжных исходных наблюдений из `series`), `facts` (массив строк с численными
основаниями), `hypothesis` (строка или `null`), `limitations` (массив строк).
Для `confirmed` требуются наблюдаемые основания; собственная импутация их не
заменяет. Погодная гипотеза указывает факты, единицы и ограничения; отсутствие
событий при недостатке данных не трактуется как `normal`. Сводный статус при
наличии событий — `confirmed`, если есть подтверждённое, иначе `candidate`;
тяжесть — максимальная. Непокрытые части периода отмечаются в `limitations`.

Ответ на условный запрос выше:

```json
{
  "schema_version": "1.0", "request_id": "job-example-1",
  "area_id": "area-example-1", "input_revision": "input-example-1",
  "mode": "retrospective", "feature_profile": "ndvi-weather-v1",
  "model_version": "baseline-example-1", "method": "no_estimate",
  "status": "insufficient_data", "severity": null,
  "series": [
    {"date": "2026-06-01", "primary_ndvi": null, "value": null,
     "state": "missing", "method": null, "baseline": null, "z_score": null}
  ],
  "events": [],
  "limitations": ["Нет пригодных наблюдений и проверенного сезонного фона"]
}
```

Корректный запрос с пустыми/частичными данными возвращает `200` с результатом и
ограничениями, даже если расчёт не позволяет сделать вывод. Это завершённая
задача Go (`completed`) со статусом вывода `insufficient_data`, не сбой ML.

## Готовность и ошибки

Готовый `GET /readyz` возвращает `200` с обязательными `status="ready"`,
`schema_version="1.0"`, `feature_profiles=["ndvi-weather-v1"]`, `model_version`.
Пока модель не загружена/конфигурация неисправна — `503`, `status="not_ready"`
и безопасная строка `reason`. Готовность не зависит от спутниковых API и не
означает свободный вычислительный слот: во время расчёта `/readyz` продолжает
отвечать. B4 сверяет схему, профиль и модель с манифестом выпуска до анализа.

Все ошибки `POST` возвращаются как JSON:

```json
{"schema_version":"1.0","request_id":"job-example-1","error":{"code":"invalid_input","message":"Даты наблюдений должны быть уникальны","retryable":false}}
```

`request_id=null` допустим, только если ID нельзя извлечь из некорректного тела.
`message` безопасен для пользователя, без traceback/секретов. Диагностика остаётся
в логах с ID. `retryable` сообщает о возможности явного нового запуска после
устранения причины, но не разрешает автоматический повтор текущего POST.

| HTTP | `error.code` | `retryable` | Обработка Go |
|---|---|---|---|
| 400 | `invalid_json` | false | `failed`, код `ml_invalid_request` |
| 413 | `payload_too_large` | false | `failed`, код `ml_input_too_large` |
| 415 | `unsupported_media_type` | false | `failed`, код `ml_invalid_request` |
| 422 | `invalid_input` | false | `failed`, код `ml_invalid_request` |
| 422 | `unsupported_contract` | false | `failed`, код `ml_contract_mismatch` |
| 429 | `busy` | true | `failed`, код `ml_busy`, предложить повтор позже |
| 503 | `not_ready` | true | `failed`, код `ml_unavailable` |
| 500 | `internal_error` | true | `failed`, код `ml_internal_error` |

Неизвестная версия/профиль → `unsupported_contract`; дубликаты дат, неверные
ссылки на источники, интервалы или типы → `invalid_input`. NaN/Inf запрещены
во всех числах. Сбой HTTP/соединения → `ml_unavailable`, тайм-аут → `ml_timeout`.
Неверный JSON/Content-Type/размер/схема ответа, чужой request_id/input_revision,
неожиданная модель, пропущенные даты и неизвестный HTTP-статус →
`ml_invalid_response`. Такой результат не сохраняется как успешный. Ошибка ML
хранится в задаче; публичный `GET /api/jobs/{id}` по существующей задаче возвращает
её состояние с `200`, не проксирует HTTP-ошибку ML.

## Исполнение, лимиты и отмена

Стартовые настройки команды, не измеренные характеристики системы:

| Ограничение | Начальное значение |
|---|---|
| Go-процесс / фоновые исполнители | 1 экземпляр / 1 воркер-goroutine |
| Ожидающие задачи Go | 8, активная задача не входит в это число |
| Одновременные вычисления ML | 1 на весь сервис; без внутренней очереди |
| Подключение Go → ML | 3 секунды |
| Полный HTTP-вызов анализа, включая чтение тела | 120 секунд |
| Вызов ML readiness | 2 секунды |
| Тело запроса / ответа | 1 MiB / 4 MiB, без сжатия в v1 |
| Наблюдения с историческим контекстом | Не более 4096 точек |

Go и ML проверяют входные лимиты; Go читает ответ с ограничением размера до
десериализации. ML не выдаёт частичный JSON при ошибке. Лимиты площади/периода
и бюджета получения источников согласуются отдельно с B1; 120 секунд относятся
только к вызову ML. Изменения настроек согласуют B4/ML и фиксируют в README.

Go сохраняет задачу и ставит её в очередь до выдачи `202`; при заполнении
возвращает `429` публичного API и не оставляет бесхозную queued-запись. Воркер
выполняет сбор → HTTP → проверку ответа → сохранение. После рестарта Go
незавершённые queued/running помечаются failed/interrupted. В MVP автоматических
повторов и гарантий exactly-once нет; повтор пользователя создаёт новый job ID.

При удалении полигона Go помечает активные задачи `cancelled`, отменяет HTTP
через context и проверяет актуальную generation участка и состояние job перед
атомарным сохранением. После тайм-аута/отмены поздний результат не сохраняется.
Разрыв HTTP не гарантирует остановку Python: вычисление может ещё продолжаться.
ML удерживает слот до фактического завершения вычисления, даже если клиент ушёл;
следующий POST получает `429`, а не запускает второй расчёт. Обработчик readiness
и отказ `busy` должны отвечать во время вычисления. Жёсткое прерывание зависшего
нативного расчёта в MVP не обещается; восстановление — перезапуск ML. Освобождать
слот только из-за истечения клиентского тайм-аута запрещено.

## Поставка, batch и проверка контракта

Один Compose-выпуск связывает два immutable digest, schema_version,
feature_profile и model_version. B4 доставляет и при ошибке откатывает пару
образов с совместимым артефактом. Во время смены ML приём новых анализов Go
приостановлен; перед возобновлением проверяются оба сервиса и версии.

Batch `private_features.csv → submission.csv` остаётся независимой Python CLI
из того же пакета/ML-образа: ей не нужны работающие Go или HTTP-сервис. CLI и
HTTP используют общие вычислительные функции, но разные входные адаптеры.

До завершения интеграции B4 и ML проверяют:

- Общие фикстуры запроса/ответа и настоящий HTTP-вызов из Go к Python;
  отдельные случаи observed/imputed/missing и недостатка данных.
- Отбраковку неверных дат/ID/версий/типов, NaN, слишком большого тела и ответа;
  модель и набор выходных дат должны совпадать с ожиданием Go.
- Тайм-аут, занятый ML после отмены клиента, доступность readiness во время
  вычисления, отказ сервиса и явный повтор без автоматического дублирования.
- Переполнение Go-очереди, рестарт Go и удаление активного полигона без позднего
  сохранения; batch CLI по-прежнему выполняется независимо от HTTP.

Фикстуры для реализаций размещаются в backend/testdata/ml-http/; сейчас примеры
выше служат документированным контрактом, не результатом выполненных тестов.

# Расширение v1.1: профиль `ndvi-multisensor-v1`

Внесено ML 05.09.2026 и **реализовано** в `backend/ml/vegetation_ml/`, проверено
62 автотестами. Всё, что описано выше, остаётся в силе без изменений.

## Зачем расширение

Профиль `ndvi-weather-v1` передаёт только итоговый `primary_ndvi`. Но в данных
соревнования `primary_ndvi` — это склейка трёх сенсоров с разной калибровкой по
приоритету s2 → landsat → modis, и расхождение между ними достигает 0.085 по
среднему. Обученная модель почти целиком построена на том, чтобы это расхождение
снять: сенсорные смещения, слияние сенсоров одного дня, сетки пролётов, эффект
даты по соседним участкам. Ни одного из этих признаков в базовом профиле нет,
поэтому по нему работает только резервный метод.

Локально разница измерена на 9208 контрольных строках по протоколу реальной
подачи: baseline организаторов даёт RMSE 0.0944, резервный метод 0.0850,
обученная модель 0.0634. В баллах регламента это 1.69, 4.50 и 10.98.
Расширение существует, чтобы веб-сценарий получал третье число, а не второе.

## Совместимость и версии

| | `1.0` | `1.1` |
|---|---|---|
| Профили | `ndvi-weather-v1` | `ndvi-weather-v1`, `ndvi-multisensor-v1` |
| Новые поля запроса | запрещены | `indices`, `area_context`, `peers` |
| Существующий клиент Go | работает без изменений | — |

Расширение **аддитивное**: запрос `1.0` обрабатывается ровно как прежде,
`/v2` не требуется. Новые поля разрешены только вместе с
`feature_profile: "ndvi-multisensor-v1"`; их появление в базовом профиле —
`invalid_input`. Запрос расширенного профиля с `schema_version: "1.0"` —
`unsupported_contract`.

**Профиль доступен, только если процесс загрузил артефакт модели.** Список того,
что реально можно запросить, объявляет `GET /readyz` в `feature_profiles`;
запрос необъявленного профиля — `unsupported_contract`. Путь к артефакту задаёт
оператор переменной `VEGETATION_ML_MODEL`, по умолчанию `artifacts/restoration.pkl`.

`GET /readyz` дополнительно возвращает `schema_versions` — список поддерживаемых
версий схемы. Поле `schema_version` в ответе сохранено и равно `1.0` для
совместимости с существующей проверкой B4.

## Новые поля запроса

### `observations[].indices` — объект или `null`

Значения отдельных сенсоров за этот день. Все восемь ключей обязательны,
отсутствие значения кодируется `null`, не нулём:

```json
"indices": {
  "s2_ndvi": 0.4918, "s2_evi": 0.3322, "s2_ndwi": -0.4820,
  "landsat_ndvi": null, "landsat_evi": null, "landsat_ndwi": null,
  "modis_ndvi": 0.5774, "modis_evi": 0.3357
}
```

**Обязательное правило согласованности:** `primary_ndvi` точки должен точно
равняться первому непустому значению в порядке `s2_ndvi` → `landsat_ndvi` →
`modis_ndvi` (допуск 1e-9). Нарушение — `invalid_input`. Правило не формальность:
именно на нём держится определение источника наблюдения, а вместе с ним и вся
коррекция калибровки. Если B1 не может гарантировать этот порядок, использовать
расширенный профиль нельзя.

`indices` у точки с `quality` `unusable` или `missing` игнорируются: контракт
запрещает считать такую точку измерением, и ML её измерением не считает.

### `area_context` — объект или `null`

```json
"area_context": {"crop_type": "озимая пшеница"}
```

Известные значения: `зерновые`, `озимая пшеница`, `пастбища/зерновые`,
`подсолнечник`. Незнакомая культура не является ошибкой: признак получает
отдельный код «неизвестно», а в `limitations` попадает соответствующая строка.

### `peers` — массив рядов соседних участков, до 8

```json
"peers": [
  {"area_id": "AOI-0007",
   "observations": [
     {"date": "2025-06-01", "primary_ndvi": 0.51, "quality": "usable",
      "indices": {"s2_ndvi": 0.51, "...": null}}
   ]}
]
```

Точка соседа содержит только `date`, `primary_ndvi`, `quality` и `indices` —
погода, интервалы и источники соседей не нужны. Даты внутри ряда уникальны и
строго возрастают, идентификаторы соседей уникальны, сам участок в списке
соседей быть не может.

Соседи нужны для **эффекта даты** — общего сдвига наблюдений всех участков в
день съёмки. По абляции это самый весомый признак после опорной оценки: его
удаление ухудшает RMSE на 0.0041, то есть примерно на 1.2 балла метрики. Если
`peers` не переданы, расчёт выполняется, но в `limitations` указывается, что
качество ниже пакетного режима.

Соседями следует передавать участки того же региона: полезность признака
основана на том, что в один день съёмки близкие участки отклоняются от своих
сезонных кривых согласованно.

## Когда применяется обученная модель

Модель применяется, только если выполнено всё:

1. `feature_profile` = `ndvi-multisensor-v1` и `schema_version` = `1.1`;
2. артефакт модели загружен процессом;
3. у участка не менее **60** надёжных наблюдений с `indices`;
4. история покрывает не менее **2** сезонов.

Пороги 3 и 4 не формальные: сенсорные смещения, сетки пролётов и сезонная норма
на одном коротком сезоне оцениваются по шуму, и результат был бы хуже простого
сглаживания. При невыполнении любого условия работает резервный метод, а причина
записывается в `limitations` — выдавать результат резервного метода за результат
модели нельзя.

Поле `method` ответа сообщает, что применялось фактически:

| `method` | Смысл |
|---|---|
| `gradient_boosting_residual` | обученная модель |
| `gaussian_smoothing_h8` | резервный метод, сглаживание по окну наблюдений |
| `nearest_neighbour_mean` | резервный метод, среднее ближайших известных |
| `no_estimate` | восстановить нечем |

`model_version` **постоянен в пределах процесса** и описывает загруженный набор
методов (`ndvi-gapfill-<версия>+hgb` или `+fallback`), поэтому B4 по-прежнему
может сверять его с манифестом выпуска. Что применялось в конкретном запросе,
сообщает `method`, а не `model_version`.

Отдельные точки могут быть восстановлены резервным методом даже при работающей
модели — тогда их `method` отличается, а в `limitations` указано их число.

## Лимиты расширенного профиля

| Ограничение | v1 | v1.1 |
|---|---|---|
| Точек самого участка | 4096 | 4096 |
| Соседних участков | — | 8 |
| Точек у соседа | — | 4096 |
| Суммарно точек в запросе | 4096 | 32768 |
| Тело запроса | 1 MiB | 8 MiB при загруженном артефакте |
| Тело ответа | 4 MiB | 4 MiB |

Лимит тела поднят потому, что 16 сезонов истории с `indices` для участка и
восьми соседей физически не помещаются в 1 MiB. Ответ не растёт: в нём
по-прежнему по одной точке на каждую входную дату внутри `analysis_period`.
Пока артефакт не загружен, действует прежний лимит 1 MiB.

Один вычислительный слот, удержание слота после ухода клиента, доступность
readiness во время расчёта и таблица ошибок — без изменений.

## Ошибки расширения

| Условие | `error.code` |
|---|---|
| `indices`, `area_context` или `peers` в базовом профиле | `invalid_input` |
| `primary_ndvi` не совпадает с первым непустым индексом | `invalid_input` |
| `indices` заполнены, а `primary_ndvi` пуст, или наоборот | `invalid_input` |
| Повторяющиеся `area_id` соседей | `invalid_input` |
| Сам участок в списке соседей | `invalid_input` |
| Неуникальные или неупорядоченные даты соседа | `invalid_input` |
| Суммарное число точек больше 32768 | `invalid_input` |
| `ndvi-multisensor-v1` при `schema_version: "1.0"` | `unsupported_contract` |
| `ndvi-multisensor-v1` без загруженного артефакта | `unsupported_contract` |

## Что требуется от B1 и B4

* **B1** — отдавать значения сенсоров раздельно и гарантировать приоритет
  s2 → landsat → modis при сборке `primary_ndvi`; сохранять культуру участка;
  уметь отдать ряды нескольких соседних участков того же региона.
* **B4** — читать `feature_profiles` из `/readyz` и выбирать профиль по нему, а
  не по конфигурации; поднять лимит тела запроса до 8 MiB для расширенного
  профиля; передавать `method` и `limitations` в публичный результат, чтобы
  пользователь видел, чем именно восстановлена точка.

Пока B1 не отдаёт раздельные сенсоры, Go продолжает работать по `1.0` без
единой правки — это и есть смысл аддитивного расширения.
